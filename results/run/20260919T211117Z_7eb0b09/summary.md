# MobileNetV2 TensorRT Benchmark Notes

## Objective

This test run measures the inference performance of the MobileNetV2 model at FP32, TF32, and FP16 precision, both with and without CUDA Graph, plus one TF32 run with `--useSpinWait` on top of CUDA Graph.

## Metrics of interest

- Throughput
- Median latency
- Latency p99
- GPU compute median
- Enqueue median
- Enqueue / compute ratio
- Speedup vs. FP32

---

## 1) Download the ONNX model

```bash
wget https://github.com/onnx/models/raw/main/validated/vision/classification/mobilenet/model/mobilenetv2-12.onnx
```

The model was saved to the `models/` directory.

---

## 2) Inspect the model structure

```bash
polygraphy inspect model mobilenetv2-12.onnx --show layers | head -30
```

Note:

- `torch-jit-export` is the graph name auto-generated by PyTorch's exporter.
- `opset version` indicates which ONNX operator specification is used.
- Opset 12 defines the semantics of operators such as `Conv`.
- An ONNX graph contains:
  - Nodes: operations such as `Conv`, `Add`, and `Clip`
  - Initializers: learned weights and biases stored as constants

## 5) Build TensorRT engines

> This run uses a fixed profile with both min and max shapes set to `1x3x224x224`.
>
> A useful later experiment is comparing `minShapes=input:1x...` vs. `maxShapes=input:16x...` to examine batch-1 latency tradeoffs.

### FP32 build

```bash
trtexec \
  --onnx=mobilenetv2-12.onnx \
  --saveEngine=mobilenetv2_fp32.plan \
  --minShapes=input:1x3x224x224 \
  --optShapes=input:1x3x224x224 \
  --maxShapes=input:1x3x224x224 \
  --noTF32 \
  --warmUp=2000 --duration=30 \
  --profilingVerbosity=detailed \
  --exportTimes=times_fp32.json \
  --exportLayerInfo=layers_fp32.json \
  2>&1 | tee build_fp32.log
```

### TF32 build

```bash
trtexec \
  --onnx=mobilenetv2-12.onnx \
  --saveEngine=mobilenetv2_tf32.plan \
  --minShapes=input:1x3x224x224 \
  --optShapes=input:1x3x224x224 \
  --maxShapes=input:1x3x224x224 \
  --warmUp=2000 --duration=30 \
  --profilingVerbosity=detailed \
  --exportTimes=times_tf32.json \
  --exportLayerInfo=layers_tf32.json \
  2>&1 | tee build_tf32.log
```

### FP16 build

```bash
trtexec \
  --onnx=mobilenetv2-12.onnx \
  --saveEngine=mobilenetv2_fp16.plan \
  --minShapes=input:1x3x224x224 \
  --optShapes=input:1x3x224x224 \
  --maxShapes=input:1x3x224x224 \
  --fp16 \
  --warmUp=2000 --duration=30 \
  --profilingVerbosity=detailed \
  --exportTimes=times_fp16.json \
  --exportLayerInfo=layers_fp16.json \
  2>&1 | tee build_fp16.log
```

### Validate what actually ran in FP16

```bash
python -c "
import json, collections
L = json.load(open('layers_fp16.json'))
L = L['Layers'] if isinstance(L, dict) else L
c = collections.Counter()
for l in L:
    for o in l.get('Outputs', []):
        c[o.get('Format/Datatype', '?')] += 1
for k, v in c.most_common():
    print(f'{v:4d}  {k}')
"
```

Expected output:

```text
  53  Channel major FP16 format where channel % 8 == 0
   1  Channel major FP16 format where channel % 4 == 0
   1  Half
   1  Float
```

## 6) CUDA Graph benchmarking

### CUDA Graph without `spinWait`

```bash
trtexec --loadEngine=mobilenetv2_fp16.plan \
  --shapes=input:1x3x224x224 \
  --warmUp=2000 --duration=30 --useCudaGraph \
  --exportTimes=times_fp16_graph.json 2>&1 | tee bench_fp16_graph.log

trtexec --loadEngine=mobilenetv2_tf32.plan \
  --shapes=input:1x3x224x224 \
  --warmUp=2000 --duration=30 --useCudaGraph \
  --exportTimes=times_tf32_graph.json 2>&1 | tee bench_tf32_graph.log

trtexec --loadEngine=mobilenetv2_fp32.plan \
  --shapes=input:1x3x224x224 \
  --warmUp=2000 --duration=30 --useCudaGraph \
  --exportTimes=times_fp32_graph.json 2>&1 | tee bench_fp32_graph.log
```

### CUDA Graph with `--useSpinWait`

```bash
trtexec --loadEngine=mobilenetv2_tf32.plan \
  --shapes=input:1x3x224x224 \
  --warmUp=2000 --duration=30 --useCudaGraph --useSpinWait \
  --exportTimes=times_tf32_graph_spin.json 2>&1 | tee bench_tf32_graph_spin.log
```

## Results

> Speedup values are computed relative to the FP32 baseline within each table.

### Without CUDA Graph

| Metric | FP32 | TF32 | FP16 | FP16 / FP32 |
| --- | ---: | ---: | ---: | ---: |
| Throughput (qps) | 518.057 | 671.866 | 1047.750 | 2.021x |
| Median latency (ms) | 1.98047 | 1.53418 | 0.99023 | 2.000x |
| Latency p99 (ms) | 1.98950 | 1.54297 | 1.00610 | 1.980x |
| GPU compute median (ms) | 1.92773 | 1.48438 | 0.94385 | 2.042x |
| Enqueue median (ms) | 0.545898 | 0.526367 | 0.583008 | 0.936x |
| Enqueue / compute ratio | 0.2833 | 0.3545 | 0.6177 | 0.459x |
| Speedup vs. FP32 | 1.000x | 1.297x | 2.021x | 2.021x |

### With CUDA Graph

| Metric | FP32 | TF32 | FP16 | FP16 / FP32 |
| --- | ---: | ---: | ---: | ---: |
| Throughput (qps) | 573.177 | 777.122 | 1327.200 | 2.316x |
| Median latency (ms) | 1.79297 | 1.33203 | 0.79492 | 2.256x |
| Latency p99 (ms) | 1.80273 | 1.34082 | 0.81226 | 2.219x |
| GPU compute median (ms) | 1.74023 | 1.28320 | 0.74902 | 2.325x |
| Enqueue median (ms) | 0.025391 | 0.009766 | 0.009766 | 2.600x |
| Enqueue / compute ratio | 0.0146 | 0.0076 | 0.0130 | 1.123x |
| Speedup vs. FP32 | 1.000x | 1.356x | 2.316x | 2.316x |

### With CUDA Graph and `--useSpinWait`

Only TF32 was run in this configuration, so the comparison is against the TF32 CUDA Graph column above. Unlike the columns in the two tables above, the ratio here is a raw quotient of spinWait over graph, so values below 1.000x mean spinWait is lower.

| Metric | TF32 graph | TF32 graph + spinWait | spinWait / graph |
| --- | ---: | ---: | ---: |
| Throughput (qps) | 777.122 | 777.626 | 1.001x |
| Median latency (ms) | 1.33203 | 1.32520 | 0.995x |
| Latency p99 (ms) | 1.34082 | 1.33398 | 0.995x |
| GPU compute median (ms) | 1.28320 | 1.28320 | 1.000x |
| Enqueue median (ms) | 0.009766 | 0.006348 | 0.650x |
| Enqueue / compute ratio | 0.0076 | 0.0049 | 0.645x |

Note:

- `--useSpinWait` changes only how the host waits for completion, so GPU compute median is bit-identical between the two runs. The 35% cut in enqueue median is real but recovers about 3.4 µs per query against a 1.28 ms kernel.
- The end-to-end effect is within run-to-run noise: 0.5% on median latency and 0.06% on throughput. CUDA Graph has already removed the launch overhead that spinWait would otherwise help with.
